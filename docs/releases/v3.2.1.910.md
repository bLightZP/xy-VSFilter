# xy-VSFilter v3.2.1.910

Optimized native ASS rendering plus an optional libass backend, now packaged for **32-bit (Win32) and 64-bit (x64)**. Each architecture includes VSFilter, XySubFilter, the subtitle consumer, and the standalone benchmark consoles. Matching PDB symbol packages and pinned dependency sources are separate downloads.

## Changes since v3.2.1.900

- Add **Prefer libass rendering** on the Main property page, in a Rendering box below Loading, unchecked by default. Both filter paths persist the preference and refresh rendering when it changes. ASS/SSA can use libass with original script/header/event data, attached fonts, style overrides and owned output frames. Other formats and extended embedded ASS2 retain native rendering. This is an alternative for rendering compatibility; identical output between libass and native is not expected.
- Statically link **libass 0.17.4, FreeType 2.14.1, HarfBuzz 11.5.1 and FriBidi 1.0.16**. No separate libass runtime DLL is required. Add pinned source hashes, source-fetch/build integration, CI preparation and redistribution notices.
- Keep bitmap payload and grouped-key cache capacities synchronized at initialization and runtime changes. Correct zero-capacity cache bypass, ownership and identity behavior; hash all six karaoke switch words.
- Reuse two edge-blur scratch rows across passes and remove unused intermediate-image allocation while preserving integer/fractional/Gaussian rounding and output.
- Replace repeated ASS command-string creation/prefix hashing with an immutable trie over source spans, preserving legacy prefix matching and malformed-tag behavior. Share eligible scalar strings/conversions in a bounded renderer-local cache, with locale/rounding/precision guards and legacy fallbacks.
- Compact cold tag programs into lazy packed stable-node blocks, keep the first owned argument inline, combine parameter headers/spill slots, construct only live strings and combine shared-owner allocations. x64 tag nodes shrink **128 → 64 bytes**; Win32 **72 → 40 bytes**. x64 parameter headers shrink **40 → 24 bytes**; Win32 **20 → 12 bytes**.
- Avoid repeated source-text, font/style and shared-owner copies; build eligible single-word layouts directly. Retain immutable uniform-span layouts/path prototypes and reuse appearance-only evaluation while preserving source/style/geometry context checks and fallback behavior.
- Prepare eligible upcoming events synchronously within measured render calls, retain eligible static vector work, recognize constant drawing-mode/baseline commands and scan polygon command spans without repeated whole-string rewrites. Reuse eligible final draw descriptors and painted bounds without borrowing expired frame storage.
- Reuse sorted active-event order and schedule expiry work at relevant boundaries. Consolidate per-event draw storage, frame grouping metadata, initial memberships and rectangle IDs; reserve final draw slots and deduplicate vertical boundaries before grouping. x86 uses borrowed grouped-key probes; x64 retains the measured stable owned-key path.
- Combine word/layer paint-machine ownership in one allocation, materialize flyweight keys only on lookup misses, and weakly retain clip masks while existing owners keep them alive.
- Fuse exact single-color packed mask generation and SSE2 alpha blending, avoiding intermediate alpha-image traffic. Planar, additive and multicolor paths retain their established implementations.
- Add console full-render, isolated parse/reconstruction, composition-replay and streaming-packet benchmarks; verified single-CPU/Above Normal scheduling; phase/allocation diagnostics; stronger Debug player/helper/module validation; additional synthetic regression scripts and ownership/grammar/cache contracts. Update the architecture graph and optimization reviews.

Native optimization eligibility is based on subtitle operations and rendering context, with no special cases for the benchmark filename, style names or timestamps. Extra retained memory is bounded separately: **64 MiB syntax, 64 MiB reconstruction, 32 MiB layout**, a sub-1-MiB empty-event pool and a sub-512-KiB scalar cache. These admissions are not a total process-memory ceiling. The default bitmap cache remains **64 entries**.

## Fresh comparison with v3.2.1.900 and the original fork

| Native build | Mean request | p99 request | Requests above 41.708 ms, per pass |
| --- | ---: | ---: | ---: |
| Original fork / Win32 | 63.88 ms | 201.60 ms | 1195–1197 |
| v3.2.1.900 / Win32 | 14.18 ms | 72.90 ms | 52–54 |
| **v3.2.1.910 / Win32** | 8.78 ms | 34.35 ms | 8–9 |
| **v3.2.1.910 / x64** | 8.81 ms | 35.76 ms | 11–12 |

On Win32, mean native request time is **38.1% lower (1.61× faster) than v3.2.1.900**, and **86.2% lower (7.27× faster) than the original fork**. Win32 p99 is **52.9% lower than v3.2.1.900**. The x64 row reports the new native x64 build; v3.2.1.900 had no published x64 package, so no x64-to-x64 release speedup is claimed.

The original-fork baseline is pinterf commit `4911cacb102bc0cbd41449793e54473265b04e62`. The v3.2.1.900 baseline is the preserved measured executable named in that release's provenance; its twelve renderer source snapshots were verified against the published tag. The original and v900 executable/toolchain builds are preserved, rather than rebuilt with the updated compiler, so these are measured build comparisons and do not isolate compiler effects.

Method: **two fresh serial processes per build**, forward/reverse order, one logical CPU (CPU 5 / affinity 0x20), **Above Normal** priority, 1920×1080, 24000/1001 fps, **64 bitmap entries**, the same extracted ASS track/private fonts, and all **2,428 frame midpoints from 22:20 to EOF**. Values are medians of per-pass statistics. Timers surround production RenderEx, excluding source/font loading and bitmap hashing; new synchronous preparation remains inside the timed calls. Full-script input makes future events available. These are offline request times, not playback drops or a streaming-delivery guarantee. Two passes do not establish worst-case latency, and other PC activity can still affect results.

The preceding development comparisons separately recorded **13.32% lower x64 full-render CPU** and **45.94% lower fixed-cohort burst time** for the general spike-reduction batch against its immediate control. The final cold-storage batch reduced peak accounted x64 syntax from **63.29 → 47.40 MiB** and zero-lead activation median from **109.21 → 106.05 ms**. These individual development gains have different controls and must not be added or presented as cumulative release speedups.

## Playback snapshot and remaining limits

The last real playback trial of the same native implementation, before this version-only bump, used freshly verified **Debug/LOCAL Zoom Player**, MPC Video Renderer, the default ASS track and **256 bitmap entries**, 22:20 through EOF:

| Graph | Renderer drops | Average whole-machine CPU | Process-tree CPU time |
| --- | ---: | ---: | ---: |
| Win32 internal | **2** | **4.79%** | 39.125 s |
| x64 helper | **2** | **5.16%** | 42.141 s |

No drops occurred in the first two seconds. Remaining drop intervals were approximately **22:47 and 23:18** on Win32, and **22:47 and 23:03** on x64. CPU includes the player, decoder, renderer, subtitle filter, helper and Debug logging, normalized across eight logical CPUs. Only one trial per architecture was requested and performed.

For historical context, the original unmodified-source playback capture recorded **1,094 drops / 78.25 CPU seconds**; v3.2.1.900's recorded final captures had **0–1 drops** (60.25 mean CPU seconds across its four unprofiled captures). Those older tests used madVR, a smaller window, different player builds and differing cache conditions. They **cannot establish a controlled relative playback improvement or regression** against this release. In particular, this release does not claim fewer drops than v3.2.1.900 or universal zero-drop playback. Short activation spikes and packet-delivery deadlines remain optimization targets.

## Correctness and reproducibility

The versioned release rebuild passed **34 focused contracts and 54 original fixture cases per architecture**, full-sample checks at **256 and zero bitmap entries**, and direct x86/x64 output comparison. All eight fresh comparison passes at 64 entries also match the original control across all 2,428 frames, with **zero pixel/bitmap-geometry/order mismatches**. All six DLL file/product versions are 3.2.1.910. The Python benchmark-metric tests pass. Fifty-two native implementation/test source hashes per architecture match the preceding validated build; the release bump changes only the version metadata in that implementation.

Native pixel preservation covers subtitle bitmap geometry, ordering and visible RGBA bytes; it is separate from libass rendering accuracy and from video presentation deadlines. The preceding unchanged native implementation also passed 17 independent full-interval scripts per architecture, retained-frame/cache-disabled checks and streaming-packet comparisons.
